# 文件存储系统 — 图表演讲稿

> 本目录下 4 张图（架构图、类图、流程图、时序图）的配套讲解。前两节是**通用话术模板**（换成任何项目都能套），后四节是**这四张图的人话版**，直接照着讲即可。

---

## 一、一句话总述

这是一个**分布式文件存储系统**：把一个大文件切成固定大小的小块，分散存到多个存储节点上。三个角色分工非常清晰——

- **元数据服务**（meta_callee）负责「**决定块放哪**」，它维护一份「文件名 → 每个块存在哪个节点」的索引，存在 MySQL 里；
- **存储节点**（storage_callee）负责「**真正存数据**」，把文件块落盘到本地磁盘；
- **客户端**（fs_caller）负责「**按方案搬运**」，它先问元数据服务拿到分配方案，再按方案把块搬到对应节点。

一句话记住：**元数据服务管"去哪"，存储节点管"存数据"，客户端管"搬"**。

## 二、每种图的讲述模板

### 架构图怎么讲

自顶向下分层讲，每层回答三件事：**为什么有这一层 → 里面有什么 → 跟谁交互**。

```
"这张图从上往下分四层。
最上面是客户端层，它要上传下载文件，所以要有…
下面是服务层，分元数据服务和存储服务两个角色…
再往下是框架核心层，它提供 RPC 通信能力…
最底下是基础设施层，是系统依赖的现成组件…"
```

**要点**：不要一个个节点念，而是「每层一句话说职责，再点一两个关键角色」。收尾落到「各层之间靠什么通信」——客户端调元数据走 ZooKeeper 发现，调存储节点走直连。

### 类图怎么讲

先讲**主角类**，再讲**关键关系**。主角是三个：`MetaService`、`StorageService`、客户端 `fs_caller`，外加一个 `ConnectionPool` 连接池。

```
"这张类图有四个主角。
MetaService 是元数据服务的实现，它现在不存内存了，改走 MySQL，靠 ConnectionPool 拿连接；
StorageService 是存储服务，负责块落盘，PutChunk 还会算个 MD5 返回；
客户端 fs_caller 是发起方，它持有一个 MprpcChannel 去发 RPC。"

"关系上，两个 Service 都继承自 proto 生成的 RpcService 接口，
MetaService 依赖 ConnectionPool 去访问 MySQL，
客户端通过 Stub 调用两个服务。"
```

**要点**：类图最容易讲成「念属性」，要避免。突出**职责**和**关系**，属性只挑一两个关键的（比如 `MetaService` 不再有内存 map，`ChunkLocation` 多了 checksum 字段）。

### 流程图怎么讲

用「骨架 → 血肉 → 收尾」三步结构，这是最通用的流程讲述法：

> [!IMPORTANT]
> **第一步：一句话说清楚"这个流程在干嘛、分几个阶段"**（骨架）
> **第二步：按阶段讲，每个阶段说清楚"为什么做 → 做了什么 → 拿到什么"**（血肉）
> **第三步：一句话收尾，说结果**

三个技巧：

1. **用「阶段」代替「步骤」**——别说"第一步第二步…第十步"，说"这个流程分三个阶段"，每个阶段内部再展开。听众只需记住 3 个阶段，而不是 10 个步骤。
2. **每个阶段用「因为…所以…」连接**——"因为要确定块放哪，所以先调元数据服务"。
3. **结尾用一句话把角色分工讲清楚**——上传流程收尾那句："元数据服务负责决定块放哪，存储节点负责真正存数据，客户端负责按方案搬运。"

### 时序图怎么讲

按时间轴讲**「谁先调谁 → 返回什么关键值 → 再调谁」**，突出关键交互和关键返回值。

```
"看这条时间线：客户端先调元数据服务的 UploadFile，元数据往 MySQL 写一笔 PENDING 记录，
返回块分配方案；然后客户端逐个块直连存储节点 PutChunk，每个块返回一个 checksum；
全部成功后再调 CommitUpload，元数据把状态从 PENDING 改成 COMPLETE 并把 checksum 存进库。"
```

**要点**：时序图最值钱的是**那几个关键返回值**（块分配方案、checksum、状态翻转），讲的时候要点名，不要只念消息名。

## 三、架构图人话版

> **这张图从下往上、还是从上往下都行，我习惯从上往下讲，分四层。**

**最上面是客户端层**。客户端要做三件事：上传、下载、删除。它不需要知道数据具体存在哪，它只做「搬运」。

**第二层是服务层**，这是核心，分两个角色：

- **元数据服务**（meta_callee）：它是整个系统的「调度中心」。以前它把索引存在内存里，一重启就丢，现在改成了 **MySQL 持久化**，存两张表——`file_meta`（文件主信息，带一个 status 状态字段）和 `file_chunk`（每个块存在哪个节点的 ip、port，还有 checksum）。上传走的是**两阶段状态机**：先登记成 PENDING，全部块传完再提交成 COMPLETE。
- **存储服务**（storage_callee）：可以部署多个，每个负责一块磁盘。块落盘的同时会**算一个 MD5 校验和返回**，还会**校验文件名**防止路径穿越攻击。

**第三层是框架核心层**，是复用的 mpRPC 框架能力：`MprpcChannel` 负责通信（既能走 ZooKeeper 发现，也能直连指定 ip:port）、`RpcProvider` 负责收请求分发、`ZKClient` 封装 ZooKeeper、`Logger` 异步写日志。

**最底下是基础设施层**，是系统依赖的现成组件：ZooKeeper（服务发现）、Protobuf（序列化）、muduo（网络库）、**MySQL（元数据持久化）**。

**收尾**：客户端调元数据服务是「走 ZooKeeper 发现」，调存储节点是「直连 ip:port」，两者分工不同——一个要动态发现，一个按方案直达。

## 四、类图人话版

> **这张类图讲四个主角，外加它们之间的关系。**

**主角一：`MetaService`（元数据服务实现）**。它最关键的转变是——**属性里已经没有了内存 map**，只剩一个 `m_nodes`（存储节点列表）。索引数据全部落到 MySQL。方法上有五个：`UploadFile`、`CommitUpload`、`CancelUpload`、`QueryFile`、`DeleteFile`，其中 `CommitUpload` 和 `CancelUpload` 是这次新增的，对应上传的「提交」和「回滚」。

**主角二：`StorageService`（存储服务实现）**。属性就是一个 `m_dataDir`（数据目录）。它的 `PutChunk` 有个关键点——**返回 checksum**；另外还有个 `isValidFilename()` 做文件名校验。

**主角三：客户端 `fs_caller`**。它不只是简单的上传下载，还有 `putChunkWithRetry`（带重试的块上传）和 `rollbackUpload`（失败回滚）这些辅助方法，说明客户端把「可靠性」扛在了自己身上。

**主角四：`ConnectionPool`（连接池）**。这是元数据服务访问 MySQL 的通道，单例，带 `getConnection()` 拿连接，背后有生产线程和回收线程。

**关系上**：

- `MetaService` 和 `StorageService` 都**继承**自 proto 生成的 RpcService 接口；
- `MetaService` **依赖** `ConnectionPool` 去访问 MySQL；
- 客户端**通过 Stub 调用**两个服务（调存储节点是直连 Stub）；
- 两个结构体值得点一下：`StorageNode` 是 ip+port，`ChunkLocation` 多了个 **checksum** 字段，对应校验和功能。

## 五、流程图人话版

### 上传流程

> **上传流程分四个阶段：先登记，再拿方案，然后逐块传，最后提交确认。**

**第一阶段，客户端先读本地文件，按固定大小（4MB）切成块。** 因为是大文件流式读取，所以边读边切，不会一次性把整个文件读进内存。

**第二阶段，客户端调元数据服务的 `UploadFile` 登记。** 元数据会在一个事务里先查重——因为要避免同名文件覆盖，所以已存在就直接拒绝——然后插入一条 PENDING 状态的记录，同时算出每个块该放到哪个节点，把「第几块存在哪个节点」的映射返回给客户端。

**第三阶段，客户端拿着分配方案逐个块直连存储节点传数据。** 因为网络可能抖动，所以每个块失败会**同节点重试 3 次**；存储节点每收一块，会**算个 MD5 校验和返回**，客户端把这些校验和攒起来。

**第四阶段，全部块传完后，客户端调 `CommitUpload` 提交。** 元数据在事务里把状态从 PENDING 翻成 COMPLETE，并把每块的校验和写进库。到这一步，这个文件才对外可见。

**如果中途任一块失败**，客户端会回滚——直连删掉已传的块，再调 `CancelUpload` 把 PENDING 记录清掉，保证不会留下「索引在、数据不全」的脏数据。

**一句话收尾：元数据服务决定块放哪、并管状态，存储节点真正存数据并算校验和，客户端按方案搬运、并在出错时兜底回滚。**

### 下载流程

> **下载流程分四步：查位置、取数据、验 MD5、拼文件。**

**第一步，客户端调 `QueryFile` 查询。** 元数据只返回 COMPLETE 状态的文件，并且把每个块的位置和校验和一起返回。

**第二步，客户端按块的位置逐个直连存储节点 `GetChunk` 取数据。** 和上传一样，失败会重试。

**第三步，每取回一块，先用 MD5 校验。** 因为要保证数据没被篡改或损坏，所以拿元数据里存的 checksum 和刚算出来的比对，不一致就报错。

**第四步，校验通过的块按顺序流式写回本地文件，下载完成。**

**一句话收尾：下载是上传的逆过程，多了一步校验——元数据告诉客户端"去哪拿、该是什么样"，客户端自己去拿、自己验。**

### 删除流程

> **删除流程分两步：先删数据，再删索引。**

**第一步，客户端先查 `QueryFile` 拿到所有块的位置，然后按节点去重。** 因为一个节点上可能存了多个块，没必要重复发请求。去重后逐个节点调删除接口，把数据块从磁盘删掉。

**第二步，所有数据块删完后，再通知元数据服务删索引。** 元数据在一个事务里删掉 `file_meta` 和 `file_chunk` 两表的记录。

**一句话收尾：先删实际数据，再删索引记录。顺序不能反——如果先删索引，数据块就变成"孤儿块"，永远没人清理了。**

## 六、时序图人话版

> **这张时序图讲的是「上传一个 5 块文件」的完整时间线，重点看三个关键返回值。**

**开场**：客户端调元数据服务的 `UploadFile`，走 ZooKeeper 发现元数据地址。元数据往 MySQL 写一笔 PENDING 记录（插 `file_meta` 和 `file_chunk` 两表），然后**返回块分配方案**——这是第一个关键返回值，告诉客户端「块 0、2、4 去节点 1，块 1、3 去节点 2」。

**中段**：客户端拿着方案，逐个块直连存储节点 `PutChunk`。注意每个块返回的不只是成功标志，还有一个 **checksum**——这是第二个关键返回值，客户端攒起来后面要用。

**收尾**：所有块传完，客户端调 `CommitUpload`，把「块序号 + checksum」一起提交。元数据往 MySQL 写第二笔——**状态从 PENDING 翻成 COMPLETE**，这是第三个关键返回值，翻完这个文件才算真正上传完成、对外可见。

**补充两句**：任一块失败会重试 3 次，还失败就回滚（`CancelUpload`）；下载时就是拿这个 checksum 去比对 MD5。
