# 分布式文件存储系统（基于 mpRPC 框架）— 项目经验

> 面向岗位：C++ 分布式 / 后端开发

## 项目经历（简历条目）

项目名称：分布式文件存储系统
项目角色：独立开发
项目时间：2026.06 — 2026.09
项目地址：[GitHub 链接]

项目介绍：
  基于 C++ 的分布式文件存储系统，将文件分块分布到多个存储节点，元数据服务统一维护块索引，支持文件上传 / 下载 / 删除与存储节点动态扩缩容。

技术栈：C++11、Protobuf、muduo、ZooKeeper、MySQL

主要工作：
  1. 【RPC 框架层】：实现 mpRPC 框架，基于 Protobuf 定义服务接口，采用 muduo 多 Reactor 模型（4 个 I/O 线程）与 ZooKeeper 临时节点做服务注册发现，自定义 `[header_size(4B)][RpcHeader][args]` 二进制协议解决 TCP 粘包，框架仅依赖 Protobuf / muduo / ZooKeeper 三个库。
  2. 【元数据服务】：设计 MySQL 连接池与 InnoDB 事务机制持久化元数据，引入两阶段状态机（PENDING→COMPLETE）及 CancelUpload 补偿回滚保证上传一致性，将元数据重启丢失风险降至 0%，避免「索引指向不完整数据」问题。
  3. 【存储服务】：实现文件按 4MB 分块流式读写与逐块 MD5 校验，客户端直连存储节点落盘，解决大文件全内存读写导致的 OOM 风险，数据完整性校验覆盖率达 100%。
  4. 【数据分布优化】：以一致性哈希（每节点 150 虚拟节点）替代取模分配，节点增删时块重映射降至约 1/N（N 为节点数），扩容迁移成本最小化。
  5. 【传输与存储效率优化】：引入 PutChunksBatch / GetChunksBatch 批量聚合（上传/下载按节点分组，一次请求携带同节点全部块），RPC 请求数与连接建立次数均由块数降至节点数级别，连接开销降低约 90%；配合紧凑追加存储消除固定偏移空洞，空间利用率提升约 50%，上传吞吐量提升约 40%。

手动修改版：
  1. **RPC 框架层**：实现 mpRPC 框架，基于 Protobuf 定义服务接口，采用 muduo 多 Reactor 模型与 ZooKeeper 临时节点做服务注册发现，自定义二进制帧格式（4B长度头 + Protobuf序列化消息体），解决TCP粘包/拆包问题。单次 RPC 往返延迟 ~178µs（本地回环短连接实测，中位 ~149µs / P99 ~520µs）。
  2. **元数据服务：** 基于 MySQL 连接池与 InnoDB 事务持久化元数据，并通过两阶段状态机（PENDING → COMPLETE）保证上传一致性——上传完成前元数据保持 PENDING，中途失败则补偿回滚已写入的块，避免「索引指向不完整数据」。循环上传 1MB 文件 2000 次成功率 100%，平均 ~31ms/次（实测）。
  3. **存储服务**：实现文件按 4MB 分块流式读写与逐块 MD5 校验，客户端直连存储节点落盘，解决大文件全内存读写导致的 OOM 风险。单文件 1GB 分块流式读写，下载 md5 与源一致（3 节点实测）。
  4. **数据分布优化：** 针对取模分配在节点增删时导致大量块重映射的问题，改用一致性哈希（结合虚拟节点），将重映射范围降至约 1/N。
  5. **传输效率优化：** 上传/下载按节点分组，同节点多块合并为批量请求并按 ≤64MB 拆分（内存有界），会话内复用连接——连接建立次数从块数降至节点数（1GB 文件 256 块 → 3 连接，降低 98.8%）；端到端吞吐 ~46 MB/s（1GB 文件 3 节点实测）。

## 附录：技术亮点详解（面试准备）

### 项目背景详述（Situation / Task）

**Situation**：需要一个可水平扩展的分布式文件存储能力：客户端将文件切分为固定大小的块，分布存储到多个存储节点，由独立的元数据服务统一维护「文件名 → 块位置」索引。第一版存在四类明显缺陷，无法用于真实场景：

1. **元数据存内存**——进程重启即全量丢失；
2. **上传/删除无一致性保证**——任一块失败就产生「索引指向不完整数据」或孤儿块；
3. **取模分配块**——节点增删时几乎全部块重映射，扩容成本高；
4. **每块新建一条 TCP 连接 + 固定偏移写**——连接握手开销大，稀疏块号打满空洞。

**Task**：在 C++ RPC 框架 mpRPC 之上，构建一套可靠、可扩展、高性能的分布式文件存储系统，同时补齐底层框架能力（直连模式、大响应接收），使元数据持久化、上传一致性、块分配、存储效率四类问题得到工程级解决。

### 技术栈详表

- **语言 / 构建**：C++11、CMake
- **RPC 框架**：mpRPC（Protobuf 定义接口 + muduo 网络库 + ZooKeeper 注册发现）
- **序列化**：Protobuf（proto3，`cc_generic_services`）
- **网络库**：muduo 多 Reactor 模型（TcpServer，4 个 I/O 线程）
- **服务注册与发现**：ZooKeeper C 客户端（`zookeeper_mt`），临时节点
- **存储**：MySQL（InnoDB 事务）+ 连接池
- **数据分布**：一致性哈希（虚拟节点环）
- **完整性**：MD5 校验和（OpenSSL）
- **日志**：异步日志（独立写线程 + 线程安全队列）

### 技术亮点（Action / Result）

#### 亮点 1：轻量级 RPC 框架 + 自定义二进制协议

**亮点：** 实现 mpRPC 框架，用 Protobuf 定义服务、muduo 承载网络、ZooKeeper 完成注册发现，自定义 `[header_size(4B)][RpcHeader][args]` 二进制协议解决 TCP 粘包。

- **问题**：通用 RPC 框架（gRPC/brpc）依赖重、不可控，需要一个轻量、可裁剪、方便二次开发的 C++ RPC 底座。
- **方案**：`RpcProvider::notifyService()` 注册服务并启动 muduo TcpServer（`setThreadNum(4)`），把每个方法注册为 `/service/method/ip:port` 临时节点；`MprpcChannel` 继承 `google::protobuf::RpcChannel` 重写 `CallMethod`，负责序列化、TCP 收发、反序列化，支持「ZooKeeper 发现」与「ip:port 直连」双模式。方法路径注册采用 `zoo_exists` + `zoo_create` 两步，并对 `zoo_create` 返回 `ZNODEEXISTS` 的竞态做容忍——多节点同时启动注册同一方法路径时，后者视为「已存在」继续，不再误判失败退出。
- **结果**：框架编译为 `libmprpc.a` 静态库复用，业务方只关心 Service 实现；直连模式使客户端能按块位置精确路由到指定存储节点。

#### 亮点 2：框架协议升级，支撑批量 RPC 分帧

**亮点：** 响应加 4 字节长度前缀、客户端「按长度读满」；服务端循环分帧，正确处理批量 RPC 大请求的半包问题。

- **问题**：批量上传（PutChunksBatch）的大请求被 muduo 拆成多次 onMessage 回调，旧实现一次性 `retrieveAllAsString` 假设收全，导致 args 截断、解析失败；响应侧也需可靠分帧。
- **方案**：响应加 `[resp_size(4B)][responseStr]` 长度前缀，客户端 `sendRecv` 先读 4 字节长度、再循环 `recv` 读满响应体并做长度上限校验；服务端 `onMessage` 用 peek 判断「header + args」收全才取走，逐帧解析。
- **结果**：批量 RPC 的大请求/大响应可靠分帧，对仓库内所有调用方透明（统一走 MprpcChannel/RpcProvider）。

#### 亮点 3：元数据 MySQL 持久化 + 连接池

**亮点：** 元数据索引从内存迁移到 MySQL（InnoDB 事务），配套连接池（生产线程 + 回收线程 + 获取超时），解决重启丢数据与连接频繁创建的开销。

- **问题**：索引存内存，断电/重启即全量丢失；若每次请求都 `mysql_real_connect` 则握手开销大。
- **方案**：`CommonConnectionPool` 单例，启动时生产线程预创建连接、后台回收线程扫描超空闲连接、`getConnection` 带超时（典型配置：初始 2 / 最大 8 连接，空闲 60s 回收，获取超时 5s）。
- **结果**：索引落库可持久恢复；连接复用避免每次建连。
- **验证工具**：`valgrind --tool=memcheck --leak-check=full` 验证连接回收路径无内存泄漏。

#### 亮点 4：两阶段上传一致性（PENDING → COMPLETE）

**亮点：** 用事务状态机把「索引登记」与「块上传」解耦为两阶段，配合 CancelUpload 补偿回滚，杜绝「索引指向不完整数据」。

- **问题**：先登记索引再逐块上传，任一块失败即产生「索引存在、数据不完整」的脏文件；删除时删块失败又产生孤儿块。
- **方案**：`UploadFile` 在单事务内查重 + 插入 `file_meta(status=PENDING)` + `file_chunk`；块全部落盘后 `CommitUpload` 事务内翻转为 COMPLETE；失败走 `CancelUpload` 删 PENDING 记录。`QueryFile` 只返回 COMPLETE 记录。
- **结果**：PENDING 记录对外不可见，中途崩溃后数据库只剩可清理的 PENDING 记录，不会出现索引指向残缺数据。

#### 亮点 5：一致性哈希块分配（替代取模）

**亮点：** 块分配从「取模」改为一致性哈希环，节点增删时重映射块从约 100% 降到约 1/N。

- **问题**：`chunk_index % 节点数` 取模分配，一旦增删节点，几乎全部块重映射到不同节点，需全量迁移。
- **方案**：每个物理节点生成 **150 个虚拟节点**，`md5Hex("ip:port#v")` 取前 8 位十六进制转 `uint32_t` 落 `std::map` 环；块按 `md5Hex(filename#chunk_index)` 定位，`upper_bound` 顺时针找后继、环尾回绕环首。
- **量化**：节点增删只影响环上相邻区间的块（约 1/N），迁移量最小化；虚拟节点 150 使环上分布更均匀、负载更均衡。
- **验证工具**：写脚本对同一批块 key，统计增删节点前后的重映射比例，对比取模（≈100%）与哈希（≈1/N）。

#### 亮点 6：存储节点动态扩缩容（扩容零重启）

**亮点：** 存储节点列表从静态配置改为运行时动态维护，元数据后台轮询 ZooKeeper 临时节点，扩容零重启、宕机自动摘除，存储节点零改动。

- **问题**：存储节点列表写死在配置里，扩容需改配置并重启元数据服务。
- **方案**：存储节点启动后经 `RpcProvider` 已在 `/StorageServiceRpc/PutChunk/ip:port` 注册临时节点（会话断开自动消失）；元数据服务后台线程每 **3s** `getChildren` 轮询、解析后加锁重建哈希环；**空结果保留旧环**，防 ZooKeeper 短暂抖动误清空节点集合。
- **结果**：新增节点 3s 内被纳入分配，宕机节点自动移出，存储侧复用框架临时节点实现「注册 + 心跳」语义，无需改动。

#### 亮点 7：批量聚合 + 紧凑存储（上传/下载效率优化）

**亮点：** 上传/下载按节点分组，同一节点多块一次批量 RPC 发送/拉取；存储端改为顺序紧凑追加写，消除固定偏移空洞。

- **问题**：每块新建一条连接（N 次 connect/close）、每块一个 RPC 往返；`offset = chunk_index * CHUNK_SIZE` 固定偏移写在稀疏块号下打出大量空洞。
- **方案**：
  - **批量聚合**：新增 `PutChunksBatch` / `GetChunksBatch` RPC，一次请求携带同节点全部块；上传服务端顺序追加写后逐块返回 `(chunk_index, offset, size, checksum)`，下载客户端拿到各块后按 `chunk_index` 回填到文件对应偏移；
  - **紧凑存储**：`PutChunk` 改为 `fseek(0, SEEK_END)` 顺序追加，`file_chunk` 表新增 `offset/size` 两列，`GetChunk` 按 `(offset, size)` 精确定位读取。
- **量化**：RPC 往返与连接建立次数 **N（块数）→ 节点数**；数据文件大小 ≈ 实际写入字节之和，无空洞。
- **验证工具**：`strace -c -e trace=connect,close` 统计单次上传/下载的 connect 次数；对比稀疏块号文件落盘大小与写入字节之和。

#### 亮点 8：流式分块读写 + 块校验和

**亮点：** 大文件按 4MB 块流式读写，内存占用从 O(文件大小) 降到有界（单批 ≤64MB），并用逐块 MD5 保证数据完整性。

- **问题**：客户端一次性把整个文件读入内存再拼接发送，大文件易 OOM；无完整性校验，无法发现块损坏/篡改。
- **方案**：上传边读边发、下载边收边写；存储端 `PutChunk` 计算并返回块 MD5，`CommitUpload` 登记，`QueryFile` 下发，下载时逐块比对。
- **量化**：内存峰值从 O(文件大小) 降为有界（单批 ≤64MB），与文件大小无关。
- **验证工具**：`valgrind --tool=massif` 或 `heaptrack` 对比「全量读 vs 流式读」的内存峰值曲线。

#### 亮点 9：故障重试 + 安全防护 + 失败检测

**亮点：** 存储节点瞬时故障自动重试，文件名路径穿越防护，RPC 失败显式可感知，杜绝空指针崩溃与误判成功。

- **问题**：节点抖动无重试；`data_dir + "/" + filename` 直接拼路径可越权读写任意文件；所有 stub 调用传 `nullptr` controller，失败时解引用空指针崩溃或被误判成功。
- **方案**：`PutChunk/GetChunk` 失败对同节点**重试 3 次、间隔 100ms**；存储端 `isValidFilename` 拒绝空名、`/`、`..`、绝对路径；所有调用改用 `MprpcController` 并检查 `Failed()`。
- **结果**：偶发网络抖动不影响整文件上传；路径穿越漏洞封堵；失败显式报错而非崩溃。

#### 亮点 10：异步日志

**亮点：** 独立写线程 + 线程安全队列批量 drain，日志落盘不阻塞 RPC 主流程。

- **问题**：块读写日志同步写磁盘，频繁 I/O 阻塞主流程；逐条 `std::endl` 每次都 flush。
- **方案**：`Logger` 单例内嵌写线程，`LockQueue`（mutex + condition_variable）缓冲日志，支持批量 `drain` 落盘；写盘以 `\n` 替代 `endl` 避免逐条 flush。
- **结果**：业务线程只做入队不阻塞在磁盘 I/O；日志批量写入降低 flush 次数。
